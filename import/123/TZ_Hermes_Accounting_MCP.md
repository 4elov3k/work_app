# Техническое задание  
## Интеграция бухгалтерских документов в Hermes через MCP

**Проект:** Hermes  
**Формат развёртывания:** Docker  
**Назначение документа:** инструкция для реализации модуля создания и ведения контрагентов, договоров, счетов и актов через MCP  
**Основная организация:** ИП Мыленкова Любовь Валерьевна  
**Налоговый режим:** без НДС  

---

## 1. Цель проекта

Расширить ассистента Hermes возможностью работать с первичными бухгалтерскими документами через отдельный MCP-сервер.

Пользователь должен иметь возможность управлять документами обычными текстовыми командами, например:

- «Заведи контрагента ООО „Альфа“»;
- «Найди ЦентрТТМ»;
- «Покажи договоры с ЦентрТТМ»;
- «Создай счёт ЦентрТТМ на 24 900 рублей за продвижение сайта за август»;
- «Сделай акт по этому счёту»;
- «Сформируй акт и счёт за июль всем клиентам на ежемесячном обслуживании»;
- «Скачай счёт в PDF»;
- «Сформируй XML акта для СБИС»;
- «Проверь акт перед отправкой»;
- «Покажи неоплаченные счета»;
- «Отметь счёт оплаченным»;
- «Исправь адрес контрагента»;
- «Сделай новый акт на основании прошлого месяца».

Hermes должен:

1. распознать намерение пользователя;
2. найти необходимые данные;
3. вызвать соответствующий MCP-инструмент;
4. сформировать предварительный результат;
5. запросить подтверждение для значимых действий;
6. выполнить действие;
7. вернуть понятный итог и ссылки на созданные файлы.

## 3. Архитектура решения

Предпочтительная архитектура:

```text
Hermes
   ↓ MCP
Accounting MCP Server
   ↓
Application Services
   ↓
Database / File Storage / Document Generators
```

MCP-сервер должен быть тонким адаптером между Hermes и бизнес-логикой.

Внутри MCP-инструментов не должно быть:

- прямых SQL-запросов;
- расчёта итоговых сумм;
- ручного формирования XML;
- ручного формирования PDF;
- дублирования бизнес-логики;
- жёстко прописанных реквизитов;
- прямого доступа к произвольным файлам хоста.

Бизнес-логику необходимо вынести в сервисы:

```text
OrganizationService
CounterpartyService
ContractService
InvoiceService
ActService
DocumentService
NumberingService
FileStorageService
AuditService
```

Эти сервисы должны быть пригодны для использования:

- из MCP;
- из веб-интерфейса;
- из обычного API;
- из фоновых задач;
- из автоматических тестов.

## 4. MCP: версия и транспорт

Сначала определить, какую версию MCP поддерживает текущая версия Hermes.

Требования:

- не устанавливать автоматически самую новую предварительную версию SDK;
- закрепить точную версию MCP SDK;
- зафиксировать версию в lock-файле;
- указать выбранную версию в документации;
- проверить совместимость с Hermes;
- не использовать нестабильные возможности без необходимости.

Основной транспорт для Docker:

```text
Streamable HTTP
```

Предполагаемая точка подключения:

```text
http://accounting-mcp:3000/mcp
```

Если Hermes поддерживает только `stdio`, необходимо реализовать совместимый режим запуска.

Желательно поддержать оба режима:

```env
MCP_TRANSPORT=http
MCP_TRANSPORT=stdio
```

Бизнес-логика и перечень инструментов должны быть одинаковыми для обоих транспортов.

Старый SSE-транспорт не использовать как основной. Поддержку добавлять только при фактической необходимости.

## 5. Docker-развёртывание

Добавить отдельный сервис:

```yaml

  hermes:
    # существующий сервис

  accounting-mcp:
    # новый MCP-сервис
```

Требования к `accounting-mcp`:

- отдельный контейнер;
- доступ из Hermes по внутренней Docker-сети;
- отсутствие публичного порта по умолчанию;
- healthcheck;
- автоматический перезапуск;
- конфигурация через переменные окружения;
- постоянный том для документов;
- подключение к существующей или отдельной базе;
- контролируемый запуск миграций;
- корректное завершение работы;
- структурированные журналы.

Пример переменных окружения:

```env
MCP_TRANSPORT=http
MCP_HOST=0.0.0.0
MCP_PORT=3000
MCP_PATH=/mcp

DATABASE_URL=
DOCUMENT_STORAGE_PATH=/data/documents
ORGANIZATION_TIMEZONE=Europe/Moscow

MCP_AUTH_ENABLED=true
MCP_AUTH_TOKEN=

ALLOW_DOCUMENT_FINALIZATION=true
ALLOW_DOCUMENT_SENDING=false

```

Добавить файл:

```text
.env.example
```

Файл не должен содержать настоящие пароли, токены или ключи.

- не создавать новую запись автоматически;

Удаление должно быть мягким:


## 12. Требования к XML акта

Использовать существующий генератор УПД, если он уже реализован.

Для ИП Мыленковой без НДС акт должен формироваться как первичный документ без счёта-фактуры.

Обязательные параметры:

```xml
ВерсФорм="5.03"
КНД="1115131"
Функция="ДОП"
```

Продавец:

```xml
<СвИП
    ИННФЛ="526220116209"
    СвГосРегИП="312526227100047">
```

Для каждой строки:

```xml
НалСт="без НДС"
```

Налог по строке:

```xml
<СумНал>
    <БезНДС>без НДС</БезНДС>
</СумНал>
```

Итог:

```xml
<СумНалВсего>
    <БезНДС>без НДС</БезНДС>
</СумНалВсего>
```

Должно выполняться:

```text
СтТовБезНДС = СтТовУчНал
СтТовБезНДСВсего = СтТовУчНалВсего
```

Не должно быть:

```xml
Функция="СЧФДОП"
НалСт="0%"
НалСт="5%"
НалСт="7%"
НалСт="10%"
НалСт="20%"
```

Не должно быть числовой суммы НДС.

Если указан договор:

```xml
<ОснПер
    РеквНаимДок="Договор"
    РеквНомерДок="..."
    РеквДатаДок="...">
```

При наличии договора не должно быть:

```xml
<БезДокОснПер>1</БезДокОснПер>
```

Операция:

```xml
СодОпер="Оказание услуг"
```

XML должен проверяться:

1. стандартным XML-парсером;
2. официальной XSD-схемой УПД версии 5.03;
3. внутренними бизнес-проверками.

Не сообщать, что документ принят СБИС, если фактической отправки или загрузки не было.

## 13. Печатные формы и хранение файлов

Поддерживаемые форматы:

```text
счёт в PDF;
акт в PDF;
акт в XML УПД 5.03;
ZIP-пакет документов при необходимости.
```

Рекомендуемая структура:

```text
/data/documents/{organization_id}/{year}/{month}/{document_type}/{document_id}/
```

Пример:

```text
/data/documents/1/2026/08/invoices/123/invoice-2159.pdf
/data/documents/1/2026/08/acts/456/act-2160.pdf
/data/documents/1/2026/08/acts/456/ON_....xml
```

MCP-клиент не должен передавать произвольный путь для записи.

Имя файла формируется сервером.

Защитить систему от:

- `../`;
- абсолютных путей;
- выхода за каталог документов;
- перезаписи чужих файлов;
- подмены расширения;
- чтения произвольных файлов контейнера.

## 16. Двухэтапное подтверждение

Все значимые действия выполнять в два этапа.

### 16.1. Подготовка

Инструмент `prepare_*` возвращает:

```json
{
  "status": "confirmation_required",
  "summary": "Будет создан счёт...",
  "preview": {},
  "warnings": [],
  "confirmation_token": "...",
  "expires_at": "..."
}
```

### 16.2. Выполнение

Инструмент `commit_*` принимает:

```json
{
  "confirmation_token": "...",
  "idempotency_key": "..."
}
```

Токен подтверждения должен:

- иметь ограниченный срок действия;
- быть связан с пользователем;
- быть связан с действием;
- быть связан с хешем данных;
- становиться недействительным после изменения данных;
- быть одноразовым.

Одним токеном нельзя подтвердить другой документ, другую сумму или другого контрагента.

---

## 17. Действия, требующие подтверждения

Без подтверждения разрешены:

- поиск;
- просмотр;
- расчёт;
- предварительный просмотр;
- проверка XML;
- формирование отчёта;
- создание локального черновика без присвоения номера.

Подтверждение обязательно для:

- создания окончательного документа;
- присвоения номера;
- проведения документа;
- изменения выставленного документа;
- отмены документа;
- архивирования контрагента;
- отметки счёта оплаченным;
- отправки документа;
- массового создания;
- массового изменения.

Отправка в СБИС или по электронной почте должна быть отдельным инструментом и по умолчанию отключена.

---

## 18. Идемпотентность и защита от дублей

Все изменяющие инструменты должны принимать:

```text
idempotency_key
```

Повторный вызов с тем же ключом и теми же данными должен вернуть уже созданный результат.

Проверять дубли по:

- организации;
- контрагенту;
- типу документа;
- договору;
- периоду;
- сумме;
- связанному счёту;
- номеру;
- дате.

При обнаружении возможного дубля:

- не создавать новый документ автоматически;
- вернуть предупреждение;
- показать найденный документ;
- потребовать отдельное подтверждение.

---

## 19. Нумерация документов

Создать сервис:

```text
NumberingService
```

Нумерация должна быть:

- транзакционной;
- безопасной при параллельных запросах;
- отдельной по организации;
- отдельной по типу документа при соответствующей настройке;
- настраиваемой по году;
- без случайных дублей;
- без гонок.

Не использовать небезопасную схему:

```text
MAX(number) + 1
```

без блокировки или отдельной последовательности.

Предварительный просмотр не должен занимать номер.

Поддержать настройки:

```text
единая нумерация;
раздельная нумерация;
годовой сброс;
префикс;
суффикс.
```

---

## 20. Денежные расчёты

Не использовать `float` для денег.

Допустимо:

- Decimal;
- Numeric в базе;
- целое количество копеек;
- существующий безопасный денежный тип проекта.

Правила:

- фиксированная точность;
- серверный расчёт итогов;
- итог равен сумме строк;
- нельзя доверять итогу, переданному LLM или клиентом;
- суммы пересчитываются на сервере;
- отрицательные суммы запрещены;
- при режиме «без НДС» налог не рассчитывается.

## 21. Авторизация и права

Даже при работе внутри Docker-сети добавить аутентификацию между Hermes и MCP.

Минимальный вариант:

```http
Authorization: Bearer <service-token>
```

Токен:

- хранится в Docker secret или переменной окружения;
- не выводится в журналы;
- сравнивается безопасно;
- может быть заменён без изменения кода.

Права:

```text
accounting:read
accounting:write-drafts
accounting:issue
accounting:payments
accounting:send
accounting:admin
```

Пример:

- просмотр — `accounting:read`;
- черновики — `accounting:write-drafts`;
- проведение — `accounting:issue`;
- оплаты — `accounting:payments`;
- отправка — `accounting:send`;
- настройки — `accounting:admin`.

Не передавать входящий MCP-токен сторонним системам.

## 22. Аннотации MCP-инструментов

Если поддерживаются выбранной версией SDK, указать:

- `readOnly`;
- изменяет ли инструмент данные;
- является ли действие разрушительным;
- является ли вызов идемпотентным;
- обращается ли инструмент к внешней системе.

Пример:

```text
counterparties.search:
readOnly = true

invoices.commit_create:
readOnly = false
destructive = false
idempotent = true

invoices.cancel:
readOnly = false
destructive = true
idempotent = true
```

Аннотации не заменяют серверные проверки прав и подтверждений.

## 24. Формат ошибок

Ошибки должны быть структурированными и понятными Hermes.

Пример:

```json
{
  "code": "COUNTERPARTY_NOT_FOUND",
  "message": "Контрагент «Альфа» не найден",
  "details": {
    "query": "Альфа"
  },
  "recoverable": true,
  "suggested_action": "Уточните ИНН или создайте нового контрагента"
}
```

Основные коды:

```text
VALIDATION_ERROR
UNAUTHORIZED
FORBIDDEN
COUNTERPARTY_NOT_FOUND
COUNTERPARTY_DUPLICATE
CONTRACT_NOT_FOUND
MULTIPLE_CONTRACTS_FOUND
DOCUMENT_NOT_FOUND
DOCUMENT_DUPLICATE
DOCUMENT_ALREADY_ISSUED
INVALID_DOCUMENT_STATUS
CONFIRMATION_REQUIRED
CONFIRMATION_EXPIRED
CONFIRMATION_MISMATCH
NUMBERING_CONFLICT
XML_VALIDATION_FAILED
FILE_GENERATION_FAILED
STORAGE_ERROR
```

Пользователю не возвращать необработанный stack trace.

## 25. Диалоговые сценарии

### 25.1. Создание счёта

Пользователь:

```text
Создай счёт ЦентрТТМ на 24 900 рублей за продвижение сайта за август 2026 года.
```

Hermes:

1. вызывает `counterparties.search`;
2. находит контрагента;
3. вызывает `contracts.search`;
4. находит договор;
5. вызывает `invoices.prepare_create`;
6. показывает покупателя, договор, услугу, период, сумму и режим НДС;
7. запрашивает подтверждение;
8. вызывает `invoices.commit_create`;
9. создаёт PDF;
10. возвращает номер и ссылку на файл.

### 25.2. Создание акта из счёта

Пользователь:

```text
Сделай акт по этому счёту.
```

Hermes:

1. получает счёт;
2. переносит контрагента;
3. переносит договор;
4. переносит строки;
5. переносит сумму;
6. устанавливает режим «без НДС»;
7. вызывает `acts.prepare_create`;
8. показывает предварительный результат;
9. после подтверждения создаёт акт;
10. создаёт PDF и XML.

### 25.3. Создание контрагента

Пользователь:

```text
Заведи ООО «Альфа», ИНН 1234567890.
```

Hermes:

1. проверяет ИНН;
2. ищет дубли;
3. при наличии провайдера получает реквизиты;
4. показывает карточку;
5. после подтверждения создаёт контрагента.

### 25.4. Массовое создание

Пользователь:

```text
Создай акты за июль всем клиентам на ежемесячном обслуживании.
```

Hermes:

1. получает активные договоры;
2. подготавливает список документов;
3. показывает количество и общую сумму;
4. показывает предупреждения;
5. запрашивает отдельное подтверждение;
6. создаёт документы идемпотентно;
7. возвращает отчёт по каждому документу;
8. не прекращает всю операцию из-за одной ошибки;
9. не создаёт дубли при повторном запуске.

## 33. Критерии приёмки

Работа считается выполненной, если:

1. Hermes подключается к MCP-серверу.
2. Hermes получает список инструментов.
3. Поиск контрагентов работает.
4. Создание контрагента требует подтверждения.
5. Договор создаётся и находится.
6. Счёт создаётся как черновик.
7. Окончательное создание требует подтверждения.
8. Нумерация не создаёт дублей.
9. Акт создаётся из счёта.
10. PDF открывается.
11. XML открывается стандартным парсером.
12. XML проходит официальную XSD.
13. В акте используется `Функция="ДОП"`.
14. Используется «без НДС», а не `0%`.
15. Договор указан как основание.
16. Повторный запрос не создаёт дубль.
17. Массовая операция требует отдельного подтверждения.
18. Неавторизованный клиент не имеет доступа.
19. Секреты отсутствуют в журналах.
20. Файлы сохраняются после перезапуска контейнера.
21. Все тесты проходят.
22. Docker-сборка проходит.
23. Контрольный счёт и акт формируются для ООО «ЦентрТТМ».
24. Генератор не содержит жёстко прописанных данных контрольного примера.
25. Фактические ограничения интеграции со СБИС указаны честно.
